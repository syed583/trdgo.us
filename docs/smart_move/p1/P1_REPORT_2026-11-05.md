| Approved item | Where | How it works |
|---|---|---|

## 4. How many stocks can realistically get F3 + F5 inside their windows with 50 per run / 100 per New York day
Model (`backend/smart_move_capacity.py`, deterministic, conservative): an event is served only if both requests fall inside its own window at a run instant and inside the run and day budget; every run also pays the calendar refresh for all open or about-to-open slots plus 2 confirmations, and SPY + 11 sector ETFs once per completed session; all requests are assumed to succeed. Inputs are the owner-run calendar probe counts (vendor calendar only, not ADV20). The proxy universes are lower bounds: on Nov 6 the engine recorded 53 events while the price-floor proxy counted 33.

Week of Nov 9-13, tradable events served (weekend-heavy runs: Sat 22Z, Sun 04Z / 13Z / 20Z, then 2-3 per day):
| Universe (probe-derived) | Tradable events | Served | Missed |
|---|---|---|---|
| Broad: all US-listed | 443 | 190 (43 %) | 253 |
| Price floor >= $15 | 141 | 131 (93 %) | 10 |
| Options listed (proxy for liquid) | 119 | 113 (95 %) | 6 |
| Options and cap >= $2B | 82 | 82 (100 %) | 0 |
With only 2 runs a day at 13Z and 22Z (no extra weekend run): broad 169 (38 %), price floor 124 (88 %), options 105 (88 %), cap + options 82 (100 %). The extra capacity from the weekend schedule comes from the New York day boundary (Saturday 22Z and Sunday 04Z UTC belong to different New York days, 100 requests each).
Whole horizon Nov 9 - Dec 4: broad 301 of 553 tradable (54 %); price floor 211 of 217 (97 %); options 192 of 194 (99 %); cap + options 143 of 143 (100 %). After Nov 20 the calendar is nearly empty and everything fits.
Priority vs plain deadline order (same runs): in the broad universe priority serves every proxy-tier-A event (143 of 143 over the horizon; plain deadline order 136) for the same total (300 vs 301); in the already-filtered universes plain deadline order serves a few MORE events in total (e.g. options 192 vs 188) because it never delays an early cutoff for a higher tier. So `deadline_priority` is worth using only while the junk-heavy broad universe is in play; it is a policy choice, not a free gain.
Overhead: in this conservative model roughly 40-50 % of all requests are calendar refreshes and shared SPY/ETF evidence, so a real run schedule with fewer, fuller runs does better than the model.
Data point for validity: of the 53 events evaluated on Nov 6, 29 (55 %) produced a valid BUY / SELL / NO TRADE; the other 24 were NO VALID (including the liquidity gate). Serving an event is not the same as getting a valid prediction.

**Limit recommendation (not a request): do not raise 50 / 100 yet.** They cover the likely-liquid subset of the peak week (93-100 %) if the weekend runs are made. They cannot cover the broad universe (it needs roughly 200-300 requests on each of Sat-Wed (886 for evidence alone plus calendar and shared evidence), 2-3x the day limit). Decide on higher limits only after the first P1 supervised week shows how many served events pass ADV20.

## 5. Findings worth knowing
1. **Monday BMO is never predictable** (not tradable under the frozen rule), 60 events on Nov 9 alone in the broad universe. The old policies would spend requests on them; `deadline_priority` does not.
2. The calendar share is real: with a 50-request run, a tiered refresh may use at most 13 slot requests (+2). Far days therefore advance slowly when the evidence demand is high (by design: T1 only from leftover budget).
3. A slot is refreshed even if every event in it is untradable (Monday BMO): one request. A possible later refinement (not done): treat such slots as discovery-only.
4. `observe_snapshot`'s REMOVED logic in the older event-records module is not changed; the new change log is the authority for removal tracking under tiered refreshes.
5. State files (`calendar_slots.json`, `event_changes.jsonl`, `universe.json`) live in the collector's publish folder (`--calendar-state-dir` overrides). A dry run writes `universe.json` only; calendar state is written only by a live refresh.
6. Not tested: a real LIVE run (not permitted), real provider payload shapes beyond the existing fixtures, and the new wrapper executed on the VPS.
