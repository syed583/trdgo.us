## C. Shadow-pilot architecture and implementation plan (design only)
* **Components (a separate worker process, flag-off, not inside the live service):** event registry builder; event-level scheduler (15-minute ticks, windows release-48 h .. release-24 h, retries, degraded last-chance mode, `MISSED` ledger); request governor (daily and per-event caps, background priority, 3-concurrent rule, 429 stop); factor adapters F3, F5, F7, F8 (scored) and F1, F2, F4, F6 (capture-only); payload store; snapshot writer; shadow scorer (the 40-point rules, both variants); grader (reads `earnings_event_outcomes`); daily sealer and integrity checker; monitoring and kill switch.
* **Build order (each step offline first, all flag-off):** (1) payload store and schema on a local PostgreSQL, tests; (2) registry and scheduler with fake clock (weekend, holiday, DST, moved dates, late discovery); (3) adapters with fake providers and the V1-V8 response shapes; (4) freshness classification and suspect-window rules; (5) scorer from the frozen pre-registration with the baseline's leakage-test style; (6) grader and reports; (7) integration rehearsal on synthetic events; (8) a dry run against recorded responses; only then (9) the activation gates of section F.
* **Missing evidence and degradation:** every adapter returns MISSING with a reason code; the scorer never fills gaps; coverage is reported per prediction.
* **Resource limits:** at most one database connection (limit 15), background priority, request cap per day, kill switch.

## D. PostgreSQL schema and immutable payload storage (design verified on throw-away clusters)
* Files `design_proof/smv_schema_design.sql`, `payload_store_proof.py`, `test_design_proof.py`: **5 of 5 tests pass** (PostgreSQL 17 scratch clusters, since deleted; payload store tests need no database).
* **Schema `smv`:** `event_versions`, `payloads` (sha256 key, provider, endpoint, parameter hash, sizes, compression, relative path derived from the hash by a CHECK), `payload_verifications` (integrity checks appended, never updated), `capture_runs` (START / END / TICK rows), `input_snapshots` (factor 1-8, provider stamp, capture time, session reflected, as-of quality, freshness class, status OK / MISSING with reason, extracted numbers as JSONB, CHECK that OK implies a payload and MISSING implies a reason), `predictions` (variant, prediction version, supersedes, prereg hash, cutoff, in-window flag, bull / bear points, available weight, reason codes, explanation; CHECK that an in-window prediction was made before the cutoff), `prediction_inputs` (provenance), `seals` (daily hash chain). Every table rejects UPDATE, DELETE and TRUNCATE by trigger (tested; TRUNCATE of referenced tables is refused by PostgreSQL itself). Indexes on event keys, factor and capture time. Tests also confirm the CHECK and foreign-key rules (OK without payload, factor 9, unknown event, path not derived from the hash, public release without evidence, late prediction flagged in-window are all refused).
* **Payload files:** `payloads/ab/cd/<sha256>.json.gz`, the hash taken over the raw provider bytes. Write: temporary file in the same folder, flush and fsync, re-read and verify the hash, atomic `os.replace`, read-only attribute; the metadata row is inserted only after the file is durable, so a crash leaves at worst an orphan file (found by the scan), never a row without a file. An existing file with the same hash is never rewritten; an existing corrupt file is quarantined, not overwritten (tested).
* **Integrity checks:** `verify_all` (every file re-hashed and its path checked), orphan scan (files without rows, rows without files, leftover temporary files), daily seal = hash over the sorted payload hashes and the previous seal (any change alters the chain); run nightly and after every restore.
* **Access control (to be rehearsed on a scratch folder before launch):** payload root outside the application tree, owned by Administrators; the worker account may create files and read, not delete or rewrite them (NTFS deny entries on delete and write-data for existing files, applied after creation); the database account for the worker has INSERT and SELECT only on `smv`; reports use a read-only role. An administrator can still change files, which is why the seals and the off-machine copy exist.
* **Retention and backup:** keep everything for the whole pilot plus one year; no deletion without a written approval and a dry-run list. Nightly append-only copy of the payload folder (copy new files, never mirror deletions) plus the PostgreSQL dump taken by the existing procedure; the seal files are copied separately.
* **Backup and restore test (procedure, to be run before activation):** restore the dump into a scratch database and the payload copy into a scratch folder, run `verify_all`, the orphan scan and the seal chain comparison, compare row counts and hashes with the source; a failed restore blocks activation.

## E. Initial 40-point scoring version and hashed pre-registration (shadow only)
File `shadow/prereg_score40_v1.json`, SHA-256 **`b25bd8d7889461561405ad8ec3c225b00a9202e9c75bf4b88e3e14ef7e31eb87`** (frozen before any scorer code; it also records the hashes of the verification manifest and results and of the baseline pre-registration).
* **Points:** F3 historical reaction 15, F5 price and technical 10, F7 implied volatility 10, F8 sector and market 5; total maximum **40**; never scaled to 100; F1, F2, F4, F6 may be captured but score nothing and add no coverage.
* **F3 (15):** last up to 8 earlier reactions (at least 4 required) recomputed from regular-session candles: mean reaction > +3 % / +1.5 % gives bull 8 / 4, below -3 % / -1.5 % bear 8 / 4; share of UP reactions >= 75 % / 62.5 % gives bull 7 / 3, share of DOWN likewise bear. **F5 (10):** 20-session trend (>= 5 % strong 4 points, >= 2.5 % moderate 2), relative strength against SPY (>= 3 % 3 points, >= 1.5 % 1), extension against the 50-session mean (>= 8 % 3 points). **F8 (5):** SPY 20-session trend (>= 3 %: 2 points), sector ETF minus SPY (>= 2 %: 3 points; unmapped sector = missing). F5 and F8 direction depends on the variant: **continuation** (points in the direction of the move) and **contrarian** (swapped) are both recorded for every event; neither is selected; direction is never flipped after results; Bonferroni (2).
* **F7 (10), included only after verification:** historical availability (one year, dated) and timestamps were verified on AAPL by V6; the factor uses the option-skew label of the volatility context captured in the window (call_rich bull 10, put_rich bear 10, flat 0 points but available) and counts only if per-event conditions hold (the context date is the expected session, any iv-rank `updated_at` is not after the cutoff, the snapshot is OK and inside the window); otherwise it is missing with the failing condition as reason. Thin-name verification is an activation gate. The implied-move-to-history ratio is recorded, not used.
* **Decision:** coverage = available weight / 40, at least 0.60; **BUY** if bull >= 14, bear <= 4 and bull - bear >= 10; **SELL** mirror; otherwise **NO TRADE**. Thresholds are 35 %, 10 % and 25 % of 40, declared from the design and not tuned on any outcome. Reason codes: RULE, INSUFFICIENT_COVERAGE, BELOW_MARGIN, CONFLICT, ILLIQUID_OR_UNKNOWN (adv20 below 20 M USD), UNKNOWN_TIMING, TIMING_CONTRADICTED, STALE_EVIDENCE, OUT_OF_WINDOW, NOT_TRADABLE, SUSPECT_WINDOW. Eligible events are the timing-uncertain exploratory categories; cutoff = earliest plausible release minus 24 absolute hours in UTC and New York; entry is a market-on-close order whose deadline must follow the cutoff.
* **Evaluation:** prospective shadow predictions only, graded from `earnings_event_outcomes`; BUY / SELL / NO TRADE matrices, strict and direction-only rates with Wilson intervals, cluster-bootstrap net returns, cost and slippage sensitivity, market-adjusted returns, benchmarks (always BUY / SELL, momentum, previous reaction, coverage-matched random); **no claim before at least 100 decided calls per variant over at least 8 earnings weeks and a passed evidence audit.** The baseline's sealed validation and test data are not used.
* **Honest limits:** directional capacity of F7 is a single provider-defined label; F3's direction is the stock's own tendency; weights and thresholds are provisional; the baseline development run favoured the contrarian reading, so both variants run in parallel and nothing is chosen.
